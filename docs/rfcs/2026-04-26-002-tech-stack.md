## Language Choices

### Python — Phase 1 through Phase 4 (AI layer)

**Used for:** Orchestrator, all agents, Context Watcher, App Control, Memory, Voice STT, Resource Governor.

**Rationale:** The entire AI/ML ecosystem is Python-first. Ollama, ChromaDB, pyatspi, faster-whisper, bcc (eBPF Python bindings) all have native Python SDKs. The performance overhead of Python (a few milliseconds) is irrelevant next to LLM inference latency (500ms–2s). There is no performance argument for rewriting the AI layer in Rust — only additional development time.

**Alternatives considered:** Go (no ML ecosystem), Rust (no mature ML ecosystem, difficult async patterns for this use case), JavaScript/Node (weak systems programming story).

### Rust — Phase 3+ (Wayland compositor)

**Used for:** Wayland compositor, Neural Sphere GPU rendering.

**Rationale:**
1. **Smithay** (the best Wayland compositor library) is Rust-native. Using it from C would require unsafe FFI; reimplementing in C would take significantly longer.
2. **Performance requirement:** The compositor renders at 60fps and handles all user input. Python's GIL and garbage collector would cause visible frame jitter.
3. **Memory safety:** Compositor bugs cause visual corruption or full system freeze (no separate process sandbox). Rust eliminates use-after-free and data race bugs.
4. **Claude's Rust competence:** Claude writes correct Rust well, including lifetime management in common patterns.

**Why not C?** Smithay has no C API. wlroots (C) is an alternative but requires managing C memory for the compositor's entire object graph — high bug risk for a solo developer.

### C — Phase 4 only (eBPF programs)

**Used for:** eBPF kernel observation programs only. Approximately 3–5 files, 50–200 lines each.

**Rationale:** eBPF programs are compiled to BPF bytecode and loaded into the Linux kernel's BPF VM. The BPF verifier requires C or Rust (via the Aya framework). C is the ecosystem standard — all documentation, examples, and tooling (bcc, bpftrace, libbpf) use C. eBPF programs are small and do one thing each; C complexity is manageable at this scale.

**Alternative:** Aya (Rust eBPF framework). Not adopted because the toolchain is less mature and documentation is sparse. Revisit if C proves problematic.

## Library Choices

### Ollama

**Alternatives:** llama.cpp Python bindings, llamafile, vLLM, HuggingFace transformers.

**Chosen because:** Simplest developer API (`ollama.chat()`), handles model management (pull/update/list), GPU auto-detection, Python SDK is clean, actively maintained. vLLM is production-grade but adds operational overhead for a single-user system. llama.cpp bindings require managing model files manually.

### PyQt6

**Alternatives:** GTK4 (Python), CustomTkinter, Dear PyGui, Tauri, Electron.

**Chosen because:** QPainter enables the custom Neural Sphere animation without third-party dependencies. Frameless windows and transparency work on both X11 and Wayland (via XWayland for Phase 1). GTK4 lacks QPainter-equivalent custom drawing. CustomTkinter can't achieve the visual quality needed for the sphere animation.

### Smithay

**Alternatives:** wlroots (C), wayfire (C++), writing from scratch.

**Chosen because:** Rust-native, modular (use only the pieces needed), actively maintained, has example compositors (`smallvil`, `anvil`) to learn from. wlroots requires C and has a steeper learning curve for someone without Wayland experience.

### ChromaDB

**Alternatives:** FAISS, Qdrant, Pinecone (cloud), SQLite + manual embeddings.

**Chosen because:** Embedded (no separate server process), Python-native, clean API, actively maintained, sufficient for single-user use case. FAISS requires more setup for persistence. Pinecone is cloud-only (violates local-first principle).

### faster-whisper

**Alternatives:** OpenAI Whisper (slower), whisper.cpp (C++ bindings), Vosk (less accurate).

**Chosen because:** 2–4x faster than original Whisper Python, same accuracy, runs on CPU comfortably (base model ~150ms latency), straightforward Python API. Voice accuracy on base model is sufficient for clear speech.

## Model Configuration for HP Omen (4GB VRAM)

| Model | Size | Why this one |
|-------|------|-------------|
| `llama3.2:3b` | ~2.0GB VRAM | Fits in 4GB VRAM. Fast enough for interactive overlay (~20 tok/sec on GTX 1050 Ti). |
| `moondream` | ~1.5GB VRAM | Lightweight vision model. Runs alongside llama3.2:3b. Good screen description quality. |
| `nomic-embed-text` | ~0.6GB | Fast embeddings for ChromaDB. Batch-able. |
| `faster-whisper base` | CPU only | 150ms latency on CPU. No VRAM needed. |

**Hard constraint — do not use:**
- `llama3.1:8b` — 4.5GB VRAM, won't co-exist with vision model. CPU fallback = 5–8 tok/sec, too slow.
- `llama3.2:11b-vision` — exceeds 4GB VRAM entirely.

**Cloud fallback via MCP:** When local model is insufficient for a complex task, user can configure Anthropic/OpenAI API key in `config.toml`. The Orchestrator routes to the cloud model for that request only.
